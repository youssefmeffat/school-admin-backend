# Enhancement pass -- 2026-08-19

This document describes exactly what changed in this pass, why, and how each
change was verified. The existing codebase (v3.1.0) was already a mature,
well-engineered system -- intent classification fast paths, schema-scoped
caching, a real SQL validator (multi-statement/write/alias/unknown-table
checks), a repair loop, lazy semantic learning, etc. Rather than rewriting
working code, this pass:

1. Audited the pipeline end-to-end with a purpose-built stress harness
   (richer schema: FK relationship, nullable numeric column, nullable FK,
   nullable date column) and a deterministic rule-based fake LLM backend,
   so every claim below is something that was actually run, not assumed.
2. Fixed the real bugs that harness surfaced.
3. Made two targeted, verified performance improvements.
4. Replaced the single 4-test smoke suite with a 47-test suite covering
   every edge-case category from the spec.

No dependency, public API, or config default was removed. Existing tests
(`tests/test_dynamic_semantics.py`) still pass unmodified.

## Correctness fixes (highest priority per the stated priority order)

### 1. Rule #7 ("reject unsupported entities") was implemented but dead code

`Text2SQLPipeline._requested_entity_is_unavailable()` existed and was fully
implemented, but nothing in `ask()` ever called it. A question like "how
many restaurants are there?" against a schema with no restaurant-like
table/column would fall through to normal SQL generation, and depending on
the model's behavior could silently query an unrelated table instead of
being rejected.

**Fix:** wired the check into `ask()`. Placement matters: it now runs
*after* targeted semantic learning (`_learn_semantics_for_question`), and
was extended to also check learned table/column synonyms
(`self.semantic_schema[...].synonyms`) and user-taught mappings
(`self.user_memory`), not just literal schema/table names. This preserves
rule #3 (dynamic synonym resolution, e.g. "workers" -> Employees) while
still rejecting genuinely absent concepts (e.g. "restaurants" against an
employee/department schema).

Added `_answer_unavailable_entity()` to produce a clear, honest rejection
message listing the tables that *are* available.

**Verified:** `tests/test_edge_cases.py::TestUnsupportedEntities` (3 tests)
and `TestSynonymResolution` (2 tests) -- confirms "workers" still resolves
via synonym learning while "restaurants"/"customers" are correctly
rejected, and that a rejected question doesn't corrupt pipeline state for
the next (valid) question.

### 2. NULL-sorting bug in highest/lowest queries (rules #5 and #6)

Empirically confirmed: for `ORDER BY salary ASC LIMIT 1` on a column with a
NULL value, SQLite (and standard SQL generally) sorts NULL before every
real value, so the query silently returns the row with a *missing* salary
as the "lowest paid" employee instead of the true minimum. This is a
correctness bug that would produce a confidently wrong, unflagged answer --
exactly what rule #13 ("answers must use ONLY actual query results; never
invent facts") is meant to prevent, since a NULL is not really a value at
all.

**Fix:** added `Text2SQLPipeline._missing_null_guard_error()`, wired into
the existing `_question_sql_alignment_error()` check that already runs
before every SQL execution. When a highest/lowest/top/bottom question's
`ORDER BY` column is known (from schema metadata) to be nullable, and the
SQL has no `IS NOT NULL` filter (or `NULLS LAST/FIRST` clause) for that
column, the alignment check now raises a validation error with a precise
message, which feeds directly into the existing repair loop so the model
gets one more attempt with the exact reason -- consistent with rule #12.

Deliberately conservative: only fires when the *ordered* column is verified
nullable in the actual schema (never guesses), and is skipped entirely for
non-nullable columns such as primary keys (verified this doesn't produce
false positives, e.g. `ORDER BY id DESC LIMIT 1` is untouched).

**Verified:**
- `tests/test_edge_cases.py::TestNullHandling::test_lowest_salary_excludes_null_row`
  -- confirms the pipeline returns Frank ($51,000, the true minimum) rather
  than Eve (NULL salary) for "who has the lowest salary".
- `test_missing_null_guard_is_caught_by_validator_hook` -- confirms a
  backend that never adds the guard fails cleanly rather than returning
  the NULL row.
- Manually confirmed a non-nullable `ORDER BY id DESC LIMIT 1` query passes
  through with zero repair attempts (no false positive).

### 3. `their`/`his`/`her` follow-up pronouns were not recognized as ambiguous

Rule #4 explicitly calls out "their", "those", "it" as example follow-up
references that must be preserved/handled. `intent.py`'s
`_VAGUE_REFERENT_RE` covered `it|that|this|them|those|the order|the
one|the record` but not `their/his/her/its` -- so "what about their
salary?" asked with no prior conversation context would *not* be flagged
as ambiguous and would be sent straight to SQL generation with an
unresolved pronoun.

**Fix:** added `their|theirs|his|her|hers|its` to `_VAGUE_REFERENT_RE`.

**Verified:** `tests/test_edge_cases.py::TestAmbiguousFollowUps` (2 tests)
-- confirms a bare pronoun with no context is now flagged for
clarification, while the same pronoun *with* conversation context is
correctly allowed through (existing behavior for the context-aware case
was already correct and is preserved).

## Performance improvements

### 4. Persistent per-provider executor instead of one-per-query thread pool

`db_providers.py`'s `_run_with_timeout()` (used by every single
`provider.execute()` call, i.e. every SQL execution against the target
database) previously created and tore down a brand-new
`ThreadPoolExecutor` on *every query*. Both `SQLAlchemyProvider` and
`SQLiteFallbackProvider` now lazily create one reusable single-worker
executor per provider instance (disposed in `close()`), and
`_run_with_timeout()` accepts an optional externally-owned executor so it
no longer spawns/tears down an OS thread per call.

This is a pure implementation-detail change -- the timeout contract is
identical (still enforced with `future.result(timeout=...)`), and a
caller-owned executor is never shut down inside `_run_with_timeout` itself
(only a locally-created fallback executor is, preserving the original
"don't block on shutdown after a timeout fires" guarantee).

**Verified:**
- All existing + new tests still pass (thread-pool lifecycle change is
  fully covered by the suite exercising `provider.execute()` repeatedly).
- Manually confirmed the timeout still fires correctly on a slow query
  (`WITH RECURSIVE ...`) and that the provider is still usable for
  subsequent queries afterward (single-worker reuse doesn't wedge).
- Benchmarked 200 sequential `SELECT COUNT(*)` calls against the reused
  executor: ~0.32 ms/query overhead from the timeout machinery, down from
  a fresh thread-pool create+teardown on every call.

### 5. Cache-hit path confirmed near-zero cost

Not a new change (the LRU query cache already existed and was already
checked before schema/retrieval work), but verified end-to-end: a
cache-hit `ask()` call completes in ~0.06 ms versus ~22 ms for the cold
path (schema introspection + profiling + retrieval + semantic learning +
generation) in this synthetic benchmark. With a real local LLM the
absolute cold-path number will be dominated by model inference, so the
relative benefit of the cache (skipping retrieval + generation entirely)
is even larger there.

### Considered and deliberately deferred

Parallelizing `StatisticsService.analyze()` (one query per table during
schema load) across tables was considered, since it's the main sequential,
N-round-trip cost in `learn_schema()`. It was **not** implemented: the new
persistent per-provider executor (item 4) is single-worker, so naive
concurrent calls from multiple threads would simply queue on it rather
than run in parallel, and safely increasing worker count would need
per-dialect connection-pool sizing considerations for network databases.
Given the priority order in the spec (**correctness > schema grounding >
safety > speed**), this was left alone rather than risking a
half-verified concurrency change.

## Test suite

Replaced the single-file, 4-test smoke suite with:

- `tests/test_dynamic_semantics.py` -- **unchanged**, still passes.
- `tests/test_edge_cases.py` -- **new**, 43 tests across 15 categories:
  synonyms, unsupported/wrong entities, ambiguous follow-ups, missing
  columns, large results, NULL handling, joins, dates, malformed input,
  SQL injection/write attempts, complex filters, highest/lowest-entity
  correctness, caching, greetings/small-talk/offensive-input fast paths,
  and user teaching -- plus two schema-introspection sanity checks (FK
  discovery, nullable-flag discovery).

Run everything with:

```bash
cd text2sql_project        # the directory containing this text2sql/ package
PYTHONPATH=. python3 -m unittest text2sql.tests.test_dynamic_semantics text2sql.tests.test_edge_cases -v
```

**Result: 47/47 passing.**

Both test files use deterministic fake LLM backends (no model download, no
network access, sub-second total runtime), following the same pattern the
original test file already established.

## What was intentionally *not* touched

Given the size of this codebase (~10,000 lines across 24 modules) and the
priority order in the spec, this pass focused on verified, load-bearing
issues rather than a speculative full rewrite. Modules not touched
(`semantic_learning.py`, `retrieval.py`, `synthetic_sql.py`,
`finetune.py`, `evaluation.py`, `recommendations.py`, etc.) were read and
spot-checked but no concrete bug or measurable bottleneck was found in
them during this pass.
